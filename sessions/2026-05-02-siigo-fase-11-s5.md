## Avance

### `siigo-poll-status/index.ts` (~180 líneas)

Flujo:
1. **Método** — solo POST (405 si no).
2. **Auth** — `Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>` exacto. Comparación directa contra la env. Sin `auth.getUser` — el cron no es usuario.
3. **Limit** — query string `?limit=N` (clamp a [1, 50]; default 20). Útil para tests manuales.
4. **`get_invoices_for_polling(limit)`** — RPC con `FOR UPDATE SKIP LOCKED` + filtro de backoff aplicado en SQL.
5. **Atajo tick vacío** — si no hay candidatos, retorna summary `{processed:0,...}` sin pedir token Siigo. Ahorra cuota de `/auth` en ticks inactivos y permite arrancar la EF antes de configurar las envs Siigo.
6. **`getSiigoToken` (lazy)** — solo se llama si hay candidatos. Si falla → 503; el cron reintenta en 30 s.
7. **Por cada candidato** (en serie, no paralelo, para respetar rate limit ~50/min):
   - `GET /v1/invoices/{siigo_id}` con `siigoFetch`.
   - `mapStampStatus` extrae estado, cufe, cude, número, urls, observations.
   - **Terminal `Stamped`/`Rejected`** → UPDATE con todo el snapshot + `last_error` solo si Rejected.
   - **No-terminal** + `attempts >= MAX_RETRIES` → `siigo_status='error_max_retries'`, `last_error='exhausted retries'`.
   - **No-terminal** + attempts < MAX → UPDATE solo `siigo_status, attempts, last_attempt_at`.
   - **HTTP error** (4xx/5xx no esperado) → contabiliza intento + last_error, sigue no-terminal.
   - **Network/timeout** → contabiliza intento + last_error.
8. **Summary** — `{processed, stamped, rejected, still_pending, errored, exhausted, duration_ms}`.

## Decisiones

- **Lazy token con atajo de tick vacío**: prevalece pragmatismo sobre la spec original que pedía token primero. Beneficios: (1) no quema cuota Siigo `/auth` cada 30 s en ticks vacíos, (2) la EF arranca y responde 200 incluso antes de configurar las envs Siigo. La spec se actualiza implícitamente con esta decisión.
- **Comparación directa con `SUPABASE_SERVICE_ROLE_KEY`**: la EF NO usa `auth.getUser` porque el cron pg_net manda el bearer literal, no un JWT firmado por el `auth` server. La comparación es constant-string; no es vulnerable a timing salvo a nivel grueso (clave de 200+ chars, riesgo despreciable). Si en el futuro se quiere endurecer, usar `crypto.subtle` para comparación constant-time.
- **`limit` query string para tests manuales**: facilita reproducir bugs (procesar 1 invoice exacto), pero clamp a 50 para no escalar accidentalmente el rate limit.
- **Procesamiento en serie, no paralelo**: con 20 candidatos × 200 ms = 4 s por tick, todavía caben 12 ticks/min × 20 = 240 candidatos/min vs. 50 req/min de Siigo. Aún así, serial respeta el budget. Si Siigo permite más, un futuro PR puede paralelizar con `Promise.all` por lotes de 5.
- **`updatePatch` incremental**: solo se setean los campos que cambian. UPDATE en Postgres es siempre "full row" pero conceptualmente el código no toca `siigo_observations` cuando no hay nuevas observations, evitando borrar accidentalmente datos previos.
- **Mensaje de error simplificado para Rejected**: tomamos `observations[0]` o un fallback. Las observaciones completas quedan en `siigo_observations` JSONB. La UI muestra el primero como hint y permite ver el resto en el modal "Ver observaciones" (Fase 11/S7).
- **DO block de des-programación previo**: necesario para que `supabase db reset` re-aplique sin error en local. En producción solo corre una vez (la primera).

## Bloqueos / Pendientes

- **`pg_cron` requiere setup post-deploy**: `ALTER DATABASE postgres SET app.siigo_poll_url = '...'` y `app.service_role_key = '...'` deben ejecutarse manualmente una vez por entorno. Documentado en el header de la migration. Pendiente ejecutar antes del go-live.
- **Disponibilidad de `pg_cron` en plan Supabase contratado**: en local viene activado automáticamente. En producción depende del plan. Fallback documentado: usar Supabase Cron Jobs UI con misma URL/frecuencia.
- **Test E2E del ciclo completo (emit → poll → Stamped)**: bloqueado hasta tener credenciales sandbox Siigo (S1).
- **`mapStampStatus` defensivo**: si Siigo cambia el shape de `stamp.status`, el polling lo trata como "no-terminal" y eventualmente agota retries. Mejora futura: alerta si más del X% de invoices llegan a `error_max_retries`.
